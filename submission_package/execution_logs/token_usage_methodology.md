# Token Usage Methodology — How We Calculated Token Counts

## 1. Overview

Claude Code does not expose a built-in token counter per investigation session.
Token usage was extracted post-hoc from Claude Code's raw session transcript
files (JSONL format) stored locally on the SIFT workstation.

---

## 2. Where Claude Code Stores Session Data

Claude Code automatically writes a JSONL transcript file for every session to:

```
~/.claude/projects/<project-path>/<session-id>.jsonl
```

For this project, session files were located at:

```
~/.claude/projects/-cases-HACKATHON-MEM-001-mcp-volatility-engine/
```

Each JSONL file contains one JSON object per line representing every message
exchanged in the session — including API responses which embed token usage
metadata in the following structure:

```json
{
  "message": {
    "usage": {
      "input_tokens": 98,
      "cache_creation_input_tokens": 449132,
      "cache_read_input_tokens": 3678642,
      "output_tokens": 92374
    }
  }
}
```

---

## 3. Identifying the Correct Session Files

Session files were matched to investigations using two signals:
1. **File modification timestamp** (`ls -l`) correlated to investigation dates
   in `execution_trace.log`
2. **File size** — larger files correspond to longer investigation sessions


## 4. Extraction Command

The following `grep` + `awk` command was run for each session file to sum all
four token fields across every line in the JSONL transcript:

```bash
grep -oE '"(input_tokens|output_tokens|cache_read_input_tokens|cache_creation_input_tokens)":[0-9]+' \
  <session-file>.jsonl | awk -F: '{sum[$1]+=$2} END {for(k in sum) print k, sum[k]}'
```

This command:
- Extracts all token count key-value pairs from every JSON line
- Accumulates totals per token type using `awk`
- Outputs the four token field totals for the session

---

## 5. Understanding the Four Token Fields

Claude's API splits token consumption into four categories:

| Field | Description |
|-------|-------------|
| `input_tokens` | Raw uncached input — typically just the short user prompt each turn |
| `cache_creation_input_tokens` | Tokens written to prompt cache for the first time (large Volatility JSON payloads on first receipt) |
| `cache_read_input_tokens` | Tokens read back from cache on subsequent turns |
| `output_tokens` | Tokens generated by the model (agent reasoning + tool calls + report) |

### Why `input_tokens` is so low (98–186 per session)

The raw `input_tokens` value is very low because almost all context was served
from cache. Each user turn in an investigation session is a short instruction
(e.g., "Investigate this image"). The large content — Volatility JSON telemetry
from each phase — was cached on first receipt and re-read from cache on every
subsequent turn.

### Why `cache_read_input_tokens` is so high (3–6M per session)

The agent re-reads the full investigation history on every turn to:
- Cross-correlate findings between phases (e.g., PIDs from Phase 1 matched against Phase 2 injection data)
- Trigger Phase 5 substantiation with awareness of all prior phase outputs
- Print the mandatory OODA state tracker after every tool call
- Attribute findings across hosts (Mnemosyne.sys cross-host campaign correlation)
- Synthesise all phase outputs into the final incident report

The same Phase 1–4 JSON payloads are re-read approximately 15–20 times per
session as the agent reasons forward through the OODA loop. Prompt caching
means each re-read costs a fraction of normal input pricing — this is the
MCP architecture's context efficiency working as designed.

## 8. Limitations

- Token counts reflect the full Claude Code session including any setup,
  test runs, and re-runs within the same session file. They are not isolated
  to a single clean investigation pass.
- The baseline assessment (MemLabs Lab 5 — raw terminal) consumed >147,000
  tokens before manual abort (documented in `baseline_assessment.md`).
  That session predates the MCP architecture and was not run via Claude Code's
  JSONL logging — the figure was observed directly from the Claude interface
  cost display.
